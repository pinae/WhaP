# Technical Basis

The basis of Fischer's Whale Pond consists of Docker containers that access the GPUs of the compute servers using the 
[Nvidia Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/index.html). 
All containers utilize the same kernel but separate their working environments using 
[Cgroups](https://en.wikipedia.org/wiki/Cgroups), making it appear to the processes within the container as if the 
container was the entire system. This allows for different Linux environments on the same server with different CUDA 
versions that cannot interfere with each other. Consequently, it is possible to grant all users root privileges 
within their containers.

The [Docker daemon](https://docs.docker.com/engine/daemon/), which manages the containers, runs on the host system. 
The configuration for each container is located in `/docker/{containername}/docker-compose.yml`. It contains 
[volumes](https://docs.docker.com/engine/storage/volumes/) that bind local directories into the containers. 
On one hand, these are project directories bound directly from the storage server via the path 
`/data/{username}/{projectname}/` as an [NFS](https://de.wikipedia.org/wiki/Network_File_System) mount. 
For `local_` containers, home directories are also bound from the local SSD using the path 
`/home/{username}/{projectname}/`. The `docker-compose.yml` file determines where these directories are mounted 
within the container's file system in the volumes section.

To configure the containers, Whale Pond uses [Ansible](https://docs.ansible.com/). To achieve this, the 
web application generates ad-hoc playbooks that set variables and then execute the 
[Ansible Role](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_reuse_roles.html) 
corresponding to the selected image. The roles are defined together with the web application in a 
mono-repository: https://gitlab.ruhr-uni-bochum.de/pinae/ml-ansible

## Web Application Structure

The web application uses [Flask](https://flask.palletsprojects.com/en/stable/) for the backend and 
[React](https://react.dev/) for the frontend. The UI elements are derived from 
[MUI Material](https://mui.com/material-ui/getting-started/), and diagrams are generated by 
[Chart.js](https://www.chartjs.org/). The backend accesses a [PostgreSQL](https://www.postgresql.org/) database using 
[SQLAlchemy](https://www.sqlalchemy.org/); additionally, an [InfluxDB](https://www.influxdata.com/) time-series 
database (2.x branch) is available for statistical data. For the developer setup, `whap/backend/docker-compose.yml` 
is used to spin up the databases. The backend API runs as a separate development server. In addition, there is a 
worker daemon that executes the playbooks using the Python module ansible_runner. The frontend provides `yarn start`. 
In total, the following four commands in separate terminals are required for the development setup:
```bash
cd whap/backend/ && docker compose up
cd whap/backend/ && pipenv run python run.py
cd whap/backend/ && pipenv run python worker.py
cd whap/frontend/ && yarn start
```

The deployment setup can be reviewed in the 
[whap role](https://gitlab.ruhr-uni-bochum.de/pinae/ml-ansible/-/tree/main/roles/whap) within the repository. 
There, the Flask application runs with [Gunicorn](https://gunicorn.org/) in its own container. 
[Nginx](https://nginx.org/index.html) serves static files and forwards API calls to the Gunicorn container. 
The worker container runs separately on a [Python image](https://hub.docker.com/_/python).

To stream the output of Ansible playbooks to the web frontend, the backend uses WebSockets with 
[SocketIO](https://socket.io/). Most React components load their data via API calls from the frontend to the 
[REST](https://de.wikipedia.org/wiki/Representational_State_Transfer)ful backend as usual; however, for logs, the 
frontend merely initiates a connection to a room belonging to the job, into which the backend subsequently 
pushes updates to the frontend.

The data for statistics is pushed directly to the InfluxDB by the script defined in 
`roles/metrics/templates/metrics.py.j2`. The web application only queries results from there at one-minute intervals.

## Docker Images

To build the images, a [Jenkins CI/CD server](https://www.jenkins.io/) listens for pushes to the 
[GitLab repository](https://gitlab.ruhr-uni-bochum.de/pinae/ml-ansible). The build process is defined in the 
[Jenkinsfile](https://gitlab.ruhr-uni-bochum.de/pinae/ml-ansible/-/blob/main/Jenkinsfile): 
First, Jenkins checks out the repository, then verifies if there were changes in roles whose names begin with 
`worker_`, and triggers docker build if changes occurred. The Dockerfiles for the `worker_` roles usually contain 
`apt install` commands to install CUDA and CuDNN, which triggers very large downloads and ultimately leads to 
very large image files. Images are slightly larger than 10GB. After building, Jenkins pushes the new image to the 
Docker registry of a [Distribution](https://github.com/distribution/distribution) container on the storage server.

When users select an image in Whale Pond and start the container, the Ansible playbook executes a `docker pull` 
for the corresponding image from the registry on the storage server. As a result, a copy of the image lands in 
the Docker daemon's cache on the compute server. The playbook then starts the container using this image as a base.

Since the images are not individualized for single users, an 
[entrypoint script](https://docs.docker.com/reference/dockerfile#entrypoint) handles this customization. 
It renames the standard user ubuntu (with UID `1000`) to the username of the WhaP user and changes the UID to the 
UID assigned in LDAP. It adjusts the standard group to the user group 
[defined in LDAP](https://www.it-services.ruhr-uni-bochum.de/services/ias/benutzergruppen_ldap.html.de), and 
additionally creates user groups for GIDs `15000`, `15300`, and `100000`, adding the Unix user to these groups. 
Furthermore, it adds the user to the `sudo` group and configures `sudo` to require no password for users in this group.
